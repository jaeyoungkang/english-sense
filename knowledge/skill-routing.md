# 스킬 라우팅 사례

요청이 왔을 때 일을 시작하기 전에 어느 스킬을 불러야 하는지 보여 주는 사례다. 스킬의 description이나 `AGENTS.md`의
라우팅 표를 바꿀 때, 작성자와 다른 LLM에게 이름을 가린 채 이 사례를 풀게 해서 바꾸기 전과 견준다(`knowledge/skills.md`).
정답은 요청을 받은 순간 부를 스킬이다. 일을 마친 뒤에 부르는 base-sync는 정답에 넣지 않는다. 그 길은 라우팅 표의 "모델이나
스킬을 만들거나 고쳤다" 행과 model-update 4단계가 맡는다(강PD 결정, #17, 2026-10-25).
"없음"인 사례는 스킬을 지나치게 부르는지 보려고 둔다. 사례는 실제로 받은 요청이나 그와 비슷한 것으로 고르고, 틀린 판단이
나오면 그 요청을 더한다. 프로젝트에 스킬을 더하면 그 스킬의 사례도 더한다. 라이브러리에서 고르는 스킬(event-tracking)의 사례 9, 10은 그 스킬을 고른 프로젝트의
라우팅 표로 푼다.

## 2026-10-26 익명 라우팅 검토

작성에 참여하지 않고 대화 맥락을 받지 않은 하위 에이전트에게 다섯 스킬의 이름을 가린 description과 요청 12개를 주었다.
위 웹앱 사례 17~22 여섯 개와 동기화·문안·모델 변경·오탈자·국소 API 수정 사례 여섯 개의 분류가 사전 정답과 일치했다.
기획과 합의된 동작의 구현, 설명만 하는 요청을 구분했다. 한국어 모델 문안·스킬 문안 작성의 경계는 해석 조건으로 남겼다.
이것은 라우팅의 초기 점검이며 스킬을 썼을 때 개발 결과가 나아졌다는 비교 실험은 아니다.

UX 라우팅 행을 더한 뒤 대화 맥락을 받지 않은 별도 에이전트에게 이름을 가린 description과 요청 여섯 개를 주었다.
디자인 기획·시안 구현·일반 설명·모델 반영·베이스 고르기·한 곳 교정의 분류가 사전 정답과 6/6 일치했다.
새 UX 모델을 실제 디자인에 사용한 효과나 사람의 사용성을 확인한 결과로 확대하지 않는다.

위 25~28과 베이스 동기화·스킬 호출 절차 수정 사례를 구분했다. 모델 수정은 model-update로,
