# 도메인 모델: 웹앱 사용자 경험 설계

사람이 화면의 정보와 조작을 이해하고, 판단·행동·실패·중단을 이어 가는 방식을 설계할 때 쓴다.
제작의 완료 판단은 `knowledge/domain/web-app-production.md`, 실제 상태·저장·권한은
`knowledge/domain/web-app-architecture.md`, 프레임워크 실행은 `knowledge/domain/nextjs-development.md`가 맡는다.
이 모델은 화면 목록이나 특정 색·서체를 정하지 않는다. 이 앱에 적용할 디자인 제안은 `docs/ux-design.md`에 있다.

## 개념

| 개념 | 뜻 |
| --- | --- |
| 사용 맥락 (context of use) | 사람이 서비스를 쓰는 목적, 기기, 장소와 제약 |
| 멘탈 모델 (mental model) | 사람이 서비스의 구성과 동작에 대해 가진 예상 |
| 정보구조 (information architecture) | 정보와 기능의 묶음, 이름과 탐색 경로 |
| 수행 맥락 (task context) | 현재 판단에 필요한 자료, 입력, 단계와 직전 행동 |
| 상호작용 상태 (interaction state) | 행동의 수신·처리·결과와 다음 가능한 행동을 사용자에게 나타낸 모습 |
| 정보 위계 (information hierarchy) | 정보와 조작 사이의 중요도와 읽는 순서 |
| 점진적 공개 (progressive disclosure) | 필요하거나 요청한 시점에 정보를 드러내는 방식 |
| 의미 역할 (semantic role) | 장면, 발문, 입력, 주 행동, 근거, 상태처럼 요소가 맡는 일 |
| 시각 체계 (visual system) | 의미 역할을 표현하는 글자·색·간격·폭·형태·움직임의 공통 기준 |
| 프로토타입 (prototype) | 특정 설계 의문을 확인하려고 일부 동작과 표현을 구현한 시안 |
| 학습 시각 자료 (learning visual) | 장면·개념·관계의 이해를 돕는 그림이나 도식 |
| 대화 맥락 (conversation context) | 같은 학습 대화를 이어 가는 데 쓰는 문제·제출·수정·이전 질답 |
| 대화 아티팩트 (conversational artifact) | 대화 안에서 고유하게 식별하고 다시 열어 조작할 수 있는 내용과 상태의 단위 |
| 작업 대상 (interaction target) | 지금 입력·수정·질문이 향하는 아티팩트와 수행 |
| 학습 문서 (learning document) | 감각 자료·문제·수행·대화를 읽을 순서와 구조로 담는 본문 |
| 목차 (outline) | 본문에 존재하는 항목의 식별과 위치를 가리키는 탐색 구조 |
| 자료 스택 (reference stack) | 추가한 참고 자료를 최근 추가 순서로 접근하게 하는 접힘·펼침 목록 |

## 관계

1. 사람은 이름·묶음·반복 위치에서 서비스의 동작을 예상한다. 정보구조가 사용자가 하려는 일과 어긋나면 기능이 있어도 어디서 시작할지 다시 해석해야 한다. 사용 맥락을 관찰하지 않고 정한 묶음이 그 사람의 멘탈 모델과 맞는지는 미확인이다.
2. 판단에 필요한 수행 맥락이 입력과 멀리 떨어지거나 이동 뒤 사라지면 사람이 그 내용을 기억하고 복원해야 한다. 화면을 나누는 것과 판단을 쉽게 만드는 것은 같지 않다. 반복 참고 자료의 위치를 유지하고 수행을 한 흐름에서 다시 읽게 하면 이 비용을 줄일 수 있다는 것은 설계 가설이다. (잠정)
3. 같은 클릭 뒤에도 수신, 처리, 저장, 외부 응답은 다른 상태다. 이를 한 성공 표시로 합치면 사람은 실제로 끝나지 않은 일을 끝난 것으로 이해할 수 있다. 상호작용 상태의 문구는 실제 상태가 확인된 범위를 넘을 수 없다.
4. 정보 위계는 글자·간격·폭·대비·순서가 함께 만든다. 요소 하나의 크기를 바꾸면 줄바꿈과 주변 밀도도 바뀐다. 시각 체계는 개별 컴포넌트의 취향보다 의미 역할 사이의 관계를 유지할 때 반복 화면을 해석하는 기준이 된다. (잠정)
5. 점진적 공개는 지금 필요하지 않은 정보의 경쟁을 줄이지만, 현재 판단에 필요한 정보까지 숨기면 탐색 부담을 만든다. 학습에서는 해설을 일찍 공개하는 일이 스스로 답할 기회를 없앨 수 있어, 일반적인 입력 도움과 정답에 이르는 도움을 구별해야 한다.
6. 같은 기능의 표현이 일관되면 앞에서 익힌 조작을 다시 쓸 수 있다. 색만으로 역할·상태를 나누면 색을 구분하지 못하는 사람에게 그 차이가 사라진다. 겉모양과 HTML 의미·키보드 행동이 다르면 보이는 조작과 실제 조작도 어긋난다.
7. 형식상 제출할 수 없는 입력, 학습 내용의 오답, 저장 실패와 외부 응답 실패는 원인과 다음 행동이 다르다. 모두를 입력 오류로 처리하면 제출 가능한 수행을 막거나, 서비스 실패를 사용자의 잘못처럼 보이게 한다.
8. 화면 폭·글자 크기·입력 방식이 바뀌면 배치가 달라도 같은 정보와 행동에 도달할 수 있어야 한다. 고정 패널이나 자동 도착한 내용이 읽기 위치·답안·초점을 가리면 수행 맥락을 잃을 수 있다.
9. 중단 뒤 이어 가려면 저장한 값뿐 아니라 무엇이 작성 중이고 무엇을 제출했는지, 어느 자료와 단계였는지를 알아볼 수 있어야 한다. 복원할 수 없는 상태를 저장된 것으로 보이게 하면 재개에 대한 멘탈 모델이 실제 수명과 어긋난다. (잠정)
10. 프로토타입으로 관찰할 수 있는 것은 그 시안이 실제로 구현한 경로에 한정된다. 조작 검사 통과는 사람이 이해했다는 근거가 아니며, 한 사람의 사용 관찰은 다른 사람의 사용성이나 학습 효과를 입증하지 않는다.
11. 학습 시각 자료는 무엇을 이해할 자료인지에 따라 필요한 정보와 설명이 다르다. 개념 사이의 관계를 이해하려는 과업에 장면의 외형만 그리면 그 관계를 전달하기 어렵다. 이미지로만 제공한 정보는 이미지를 읽지 못할 때 사라진다.
12. 대화 맥락이 질문마다 끊기면 사람은 장면과 자기 수행을 다시 설명해야 한다. 아티팩트의 현재 상태와 제출·수정·응답의 발생 순서는 다르다. 한쪽만 남으면 과거의 판단 과정과 현재 상태를 함께 이어 읽을 수 없다. 미전송 초안은 보낸 메시지가 아니다. (잠정)
13. 문서에 여러 자료와 아티팩트가 남으면 읽는 위치·펼친 자료·입력의 대상이 서로 다를 수 있다. 작업 대상을 명시하지 않으면 과거 문제에 한 질문이 새 문제의 답으로 해석될 수 있다. (잠정)
14. 같은 아티팩트의 내용이나 자료 버전이 바뀌면 예전 수행의 기준도 달라질 수 있다. 판의 표기가 같아도 저장 내용이 손상되면 화면의 문제와 응답의 기준은 어긋난다. 식별·당시 내용·수행을 함께 연결해야 무엇에 답했는지 다시 확인할 수 있다. (잠정)
15. 다음 아티팩트를 열었다는 행동은 앞선 내용을 이해했다는 증거가 아니다. 이동·제출·응답 완료와 학습의 숙달은 서로 다른 상태다.
16. 목차가 본문과 다른 항목을 갖거나 위치를 잃으면 탐색 결과가 예상과 어긋난다. 같은 항목의 식별로 본문과 목차를 만들면 추가된 자료·문제에 다시 도달할 수 있다. 문서의 구조는 대화 사건의 실제 순서를 대신하지 않는다. (잠정)
17. 최근 자료를 빨리 꺼내는 스택의 순서와 본문에 쌓인 순서는 목적이 다르다. 펼칠 때마다 본문을 재정렬하면 읽던 맥락을 잃고, 자료를 모두 펼치면 본문·입력 공간이 줄어든다. (잠정)

## 규칙

1. 정보구조·화면 이름·주 행동을 사용자가 하려는 일에 연결하고, 실제 사용 맥락과 아직 관찰하지 않은 가정을 구분한다. 개발 모듈 이름을 탐색 이름으로 그대로 쓰지 않는다. (관계 1)
2. 각 판단에 필요한 자료·질문·입력을 함께 찾을 수 있게 하고, 이동·자료 열람 뒤에도 작성 중인 내용과 돌아올 위치를 유지한다. 반복 참고 자료를 고정하면 대화·입력·초점을 가리지 않는 범위로 조절하게 한다. (관계 2, 8, 9)
3. 행동의 결과와 다음 행동을 문구로 알린다. 저장 중·저장됨·저장 실패와 외부 응답 대기·실패를 구분하고, 실제 확인한 저장 범위와 수명을 표시한다. 불필요하게 초점을 옮기지 않고 상태 알림을 제공한다. (관계 3, 7, 9)
4. 의미 역할 사이의 위계를 먼저 정하고 글자·폭·간격·대비를 함께 조정한다. 임의의 고정 높이로 본문을 잘라 위계를 맞추지 않고, 실제 긴 내용과 빈 상태를 렌더링해 확인한다. (관계 4, 8)
5. 사용법·입력 형식·판단 맥락은 먼저 제공하고, 정답·힌트·해설의 공개 시점은 승인한 학습 순서에 맞춘다. 펼침은 현재 상태와 키보드 조작을 함께 제공한다. (관계 5, 6)
6. 같은 기능은 일관된 이름과 표현으로 식별하고 상태는 글·형태와 함께 표시한다. 행동·이동·선택에는 해당 HTML 의미를 우선 사용하고, 맞춤 조작은 키보드 동작·초점까지 구현한다. (관계 6)
7. 제출 조건 오류는 입력 가까이에서 고칠 방법을 알리고, 학습 오답은 수행으로 받는다. 저장·외부 응답 실패 뒤에는 입력을 보존하고 무엇을 다시 시도하는지 명확히 한다. 편집 중 정답으로 유도하는 검증을 넣지 않는다. (관계 5, 7)
8. 좁은 화면과 확대 상태에서 읽는 순서·조작·초점을 확인하고, 고정 UI와 비동기 내용이 이를 가리지 않게 한다. 대비·리플로·목표 크기의 기준과 예외는 WCAG 원문을 따르며, 일부 검사만으로 전체 준수를 선언하지 않는다. (관계 6, 8)
9. 재개 화면에서 자료·단계·처음 제출·작성 중 수정과 실제 저장 여부를 구별한다. 없는 수행·진행률·숙달 판정을 채우지 않는다. (관계 1, 3, 9)
10. 의문에 맞는 프로토타입을 고르고 시뮬레이션·실제 동작·미구현 경계를 밝힌다. 조작 검사는 에이전트가 하고, 사람의 이해·편리함은 방법을 알려 주지 않은 과업 수행으로 관찰한다. 관찰 전 선호·효과는 미확인으로 남긴다. (관계 10)
11. 시각화할 개념과 관계를 먼저 정하고 그림이 그 관계를 표현하는지 대조한다. 본문·대체 설명을 가까이 두고, 그림이 없어도 문제·대화를 사용할 수 있게 한다. 정답을 선공개하는 문구·강조를 넣지 않는다. (관계 5, 11)
12. 아티팩트의 현재 상태와 별도로 문제·제출·수정·응답이 실제로 이어진 순서를 보존한다. 순서를 모르는 기존 기록은 추정해 섞지 않는다. 초안·보낸 메시지·준비 안내·AI 응답을 구분하고, 새 응답 때문에 과거를 읽는 위치를 강제로 옮기지 않는다. (관계 2, 3, 8, 9, 12)
13. 읽는 위치·펼친 자료와 질문 대상을 구분해 표시한다. 자료 열람이나 목차 이동만으로 질문 대상·초안을 바꾸지 않고 관련 수행·응답을 요청 대상에 연결한다. 다른 아티팩트를 읽거나 작업 대상으로 바꿔도 이미 보낸 요청의 대상은 바꾸지 않는다. (관계 12, 13)
14. 아티팩트마다 식별·자료 판·당시 내용과 수행을 연결한다. 같은 판의 신뢰할 수 있는 자료가 있으면 저장 내용도 대조하고, 다른 판은 당시 스냅샷을 읽는 일과 현재 AI로 보내는 일을 구분한다. 새 내용으로 이전 수행을 덮거나 읽지 못한 기록을 자동 합성하지 않는다. (관계 9, 14)
15. 다음 아티팩트를 열어도 이전 수행과 질답으로 돌아갈 수 있게 한다. 이동·제출·응답의 상태를 숙달·학습 완료로 표시하지 않는다. (관계 9, 12, 15)

16. 본문에 실제 추가된 자료·퀴즈에서 목차를 만들고 같은 식별자로 본문 위치에 연결한다. 앞으로 열 문항·숙달·학습 진도를 목차에 지어 넣지 않는다. 문서로 조합해도 실제 대화 사건 순서는 보존한다. (관계 1, 9, 12, 16)
17. 자료 스택은 새로 추가한 자료를 위에 놓고 자세한 자료는 한 번에 하나 펼친다. 다시 펼쳐도 본문·목차의 순서를 바꾸지 않으며 상단 높이를 제한해 입력·읽기를 확보한다. (관계 2, 8, 13, 17)

## 쟁점

- 문서 본문에 자료·퀴즈·대화를 쌓고 실제 항목에서 목차를 만들며 상단 자료를 스택으로 두는 것은 강PD가 정한 방향이다. 자료의 크기·카드 밀도·대상 표시가 읽고 쓰기에 편한지는 아직 확인하지 않았다.
- 점진적 공개가 찾기 어려움을 만들거나 재개 안내가 화면을 차지하면 공개 범위와 위계를 다시 본다. 한 화면에 모든 기능을 모으는 것으로 해결하지 않는다.

## 한계와 출처

2026-10-26 강PD가 UX 설계 모델을 준비하고 앱 디자인을 처음부터 다시 하도록 지시했다. 이번 모델은 외부 자료와
Lighthouse의 방법을 바탕으로 만든 초기 설계판이며, 강PD의 learn 기록이나 사용성 평가 결과가 아니다.
관계 2의 자료 위치 유지, 관계 4의 시각 체계와 관계 9의 재개 맥락은 이식 가설이다. 구체적 출처·원문의 범위·이식 한계는
`docs/research/web-app-ux-design.md`에 있다. WCAG 2.2는 표준이며 Understanding·APG는 해설·구현 지침이다.
Lighthouse는 `df85ac9a6f09c569d0e01b83ebdca4eebc996ea5`의 문서·코드·테스트를 읽었고 원본 테스트는 실행하지 않았다.
강PD는 이어 이미지와 터미널처럼 이어지는 AI 대화를 요구하며 소개 중심 시안의 한계를 지적했다.
그 뒤 이미지의 대상은 have 같은 표현의 감각이며, 학습은 탭 전환 대신 콘텐츠가 쌓이는 대화로 진행하고 감각 자료는 상단에 두도록 정했다.
관계 11의 이미지 역할은 W3C WAI Images Tutorial을, 관계 12는 그 요구와 기존 터미널 학습 흐름을 참고한 설계 가설이다.
대화 아티팩트와 작업 대상은 Claude Artifacts·Gemini 퀴즈의 공식 안내를 참고해 이 앱에 옮긴 설계 가설이다.
자료 버전·수행 연결과 숙달 구분은 기존 학습 요구와 구조 모델의 상태 수명에서 도출했다. 출처 사실과 이식 판단은 UX 조사 문서에서 나눈다.
일곱 문항의 상태·대상·순서·자료 복원 예측은 단위 검사와 Workers 브라우저 조작으로 대조했다. 같은 판의 본문 손상과 과거 응답의 재배치 누락을 발견해 고치고 반례 검사를 넣었다. 실제 조건과 한계는 작업 계약에 있다. 모델 없는 대조 작업·강PD의 사용 관찰은 없어 개발 효과·사용성·학습 효과는 아직 판단하지 않는다.
현재 적용 조건·실행·모델 판단은 `docs/tasks/quiz-artifacts.md`, 이전 단일 문제의 근거는 `docs/tasks/learning-workspace.md`, 조사 출처는 UX 조사 문서에 있다.

문서·목차·상단 스택 관계 16·17은 사용자 결정에서 구체화한 설계 가설이다. 현재 구현과 예측 검사는 `docs/tasks/document-workspace.md`에서 확인하며, 문서가 더 편리하다는 사용자 관찰은 아직 없다.
