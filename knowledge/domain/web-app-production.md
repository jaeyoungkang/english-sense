# 도메인 모델: 웹앱 제작

사용자가 하려는 일을 웹의 동작으로 만들고, 그 결과를 판단할 때 쓴다. 프로젝트를 진행하는 공통 방식은
`knowledge/production.md`, 구조 선택은 `knowledge/domain/web-app-architecture.md`, Next.js의 실행 의미는
`knowledge/domain/nextjs-development.md`가 맡는다. 이 모델은 제작 절차나 특정 제품의 요구사항을 담지 않는다.

## 개념

| 개념 | 뜻 |
| --- | --- |
| 사용자 과업 (user task) | 사용자가 어떤 상황에서 시작해 이루려는 일 |
| 제품 약속 (product promise) | 그 과업에서 서비스가 사용자에게 제공하기로 한 결과와 행동 |
| 수용 조건 (acceptance criterion) | 제품 약속이 성립했는지 판단할 구체적인 조건 |
| 품질 조건 (quality constraint) | 응답, 사용성, 접근성, 안전성처럼 과업이 성립하는 데 필요한 속성의 조건 |
| 검증 근거 (verification evidence) | 특정 조건에서 실제 동작을 관찰한 입력, 실행과 결과 |
| 미검증 가정 (unverified assumption) | 틀렸을 때 구현 방향이나 선택을 바꾸게 되는 아직 확인하지 않은 전제 |
| 변경 범위 (change scope) | 승인된 의미와 그 의미를 성립시키는 구현·검증의 경계 |
| 서비스 정책 (service policy) | 입력·결과·실패·수명·접근·운영·호환에서 서비스가 지원하거나 제한하는 조건 |

## 관계

1. 사용자 과업은 시작 조건과 기대 결과를 가지며 여러 화면과 처리에 걸칠 수 있다. 따라서 페이지나 버튼의 존재만으로 제품 약속이 성립했다고 볼 수 없다. Lighthouse의 제품 약속과 수용 조건 연결에서 가져온 제작 가설이다. (잠정)
2. 보이는 결과는 입력 처리, 상태 변화와 데이터 생성에 의존한다. 이미 완성된 데이터를 주입한 화면 검사는 그 데이터가 실제 경로에서 만들어지는지를 확인하지 못한다.
3. 같은 결과를 내는 기능도 응답을 기다리는 동안의 상태, 조작 가능성, 오류와 다음 행동에 따라 과업을 방해할 수 있다. 기능의 계산 결과와 품질 조건은 서로 다른 검증 대상을 가진다.
4. 미검증 가정이 틀리면 넓은 구현의 토대도 바뀐다. 그 가정을 실제 경계에서 확인하는 작은 실행은 이후 구현의 방향을 결정할 근거가 된다. 이미 확인한 가정에 새 실행 도구를 더할 이유는 이 관계에서 나오지 않는다. (잠정)
5. 변경의 영향은 수정한 파일보다 넓을 수 있지만, 언급된 모든 문서가 같은 의미의 소유자는 아니다. 어떤 변화가 문장을 거짓으로 만드는지에 따라 사용자 보장·구현 결정·증거의 소유자가 갈린다. 승인한 약속을 성립시키는 경로와 살펴볼 후속 영향을 구분해야 의미를 임의로 넓히지 않을 수 있다. (잠정)
6. 타입 검사, 빌드, 단위 검사, 브라우저 실행과 실제 배포 환경은 확인하는 조건이 다르다. 한 단계의 성공은 그 단계가 거치지 않은 경로의 성공을 뜻하지 않는다.
7. 검증 근거가 제품 약속과 연결돼야 어디가 성립했고 어디가 남았는지 판단할 수 있다. 수치로 정하지 않은 편리함이나 느낌은 기술 검사의 통과로 대신 판단할 수 없다. (잠정)
8. 서비스 정책이 미결이면 개별 수용 조건의 통과가 전체 과업의 충족을 뜻하지 않을 수 있다. 승인한 목표와 현재 관찰을 합치면 미구현·불일치가 사라진 것처럼 보인다. (잠정)

## 규칙

1. 사용자 과업마다 시작 상황, 기대 결과와 실패했을 때의 다음 행동을 제품 약속으로 적고 수용 조건을 연결한다. 이 제품의 약속은 `docs/learning-service.md`가 소유한다. (관계 1, 3)
2. 수용 조건이 의존하는 입력·데이터 생성·저장이나 분기까지 검증 범위에 포함한다. 화면 fixture만 확인했으면 그 범위만 근거로 보고한다. (관계 2, 6)
3. 기다림, 빈 결과, 실패, 재시도, 키보드와 모바일 조작에서 사용자가 과업을 이어 갈 수 있는지 확인한다. 기술 처리의 성공 표시와 실제 반영 상태를 맞춘다. (관계 3)
4. 실패하면 선택을 바꿀 미검증 가정이 있을 때만 그 가정을 통과하는 최소 실행을 고른다. 제품과 다른 대체 구현으로 가정을 확인한 척하지 않는다. (관계 4)
5. 변경하는 의미와 최소 구현·검증 경로, 살펴볼 후속 영향, 호환 처리를 한 작업 계약에서 구분한다. 내부 이름만 바뀌면 약속의 의미를 유지하고, 참·거짓 기준이 바뀌면 수용 조건의 변경을 드러낸다. 새 의미를 요구하는 후속 변경은 이번 범위에 조용히 끼워 넣지 않는다. (관계 5)
6. 수용 조건마다 실제 실행 방법·결과·확인하지 못한 조건을 연결한다. 검사 이름이나 mock 응답을 실제 실패 유발의 근거로 읽지 않는다. 배포 환경에 의존하는 기능은 해당 런타임에서 확인한다. (관계 2, 6, 7)
7. 자동으로 판정할 수 있는 동작과 사람이 사용해 판단할 품질을 나눈다. 편리함과 학습 효과를 구현 검사만으로 확정하지 않는다. (관계 3, 7)
8. 과업에 필요한 서비스 정책을 채택·미지원·미결로 가르고, 채택한 목표와 현재 구현·근거를 따로 적는다. 일부 조건의 성공으로 미결 정책이나 다른 경로까지 완료로 올리지 않는다. (관계 6, 8)

## 쟁점

- Lighthouse에서 가져온 약속·수용 조건·변경 범위 기법은 이 개인용 서비스에서 아직 사용 효과를 확인하지 않았다.
- 조건이 많은 변경을 문서만 늘려 닫으려 하면 구현과 사용자 관찰이 밀릴 수 있다. 기록은 현재 판단을 바꾸는 근거에 한정한다.

## 한계와 출처

2026-10-26 강PD는 웹앱 제작·웹앱 아키텍처·Next.js 개발 모델을 나누고, Lighthouse의 기획·구현 기법을 모델과 스킬로 차용하도록 지시했다.
원문 사실, 차용 판단과 이번 구현에서 관찰한 것은 `docs/research/lighthouse-methods.md`에서 구분한다.
Lighthouse 기준은 `df85ac9a6f09c569d0e01b83ebdca4eebc996ea5`이며, 해당 저장소의 테스트를 이번에 실행하지 않았다.
관계 1·4·5·7은 그 프로젝트의 절차에서 끌어낸 이식 가설이다. 관계 2·6은 이번 이관의 정적 자산 실패와 실제 브라우저 검사로도 관찰했으나 강PD의 학습 수행 기록은 아니다.
W3C 상태 알림·초점 안내와 Playwright의 사용자 동작 검증 원칙은 같은 조사 문서에서 연결한다. 제작 절차는 `.claude/skills/web-app-planning/SKILL.md`와 `.claude/skills/web-app-implementation/SKILL.md`가 맡는다.
서비스 정책·소유권·근거의 세부 연결과 원문에서 발견한 불일치는 `docs/research/lighthouse-contract-engineering.md`에 있다.
관계 5의 소유권 기준과 관계 8은 같은 원문에서 이식한 가설이며 이 앱의 출시·개발 효과로 검증하지 않았다.
