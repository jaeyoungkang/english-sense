# 도메인 모델: Next.js 개발

Next.js에서 URL, 컴포넌트, 데이터와 실행 환경을 어떻게 연결할지 판단할 때 쓴다. 웹앱의 일반 구조와 저장·실패의
원리는 [웹앱 아키텍처](web-app-architecture.md)가, 제작의 판단과 검증 범위는 [웹앱 제작](web-app-production.md)이 맡는다.
이 문서는 그 원리를 복사하지 않고 Next.js의 작동을 설명한다. 명령과 환경 설정은 `README.md`에 있다.

## 개념

| 개념 | 뜻 |
| --- | --- |
| App Router | `app/`의 파일과 폴더로 URL과 화면의 구성을 표현하는 Next.js 라우터 |
| 페이지(page) | 한 경로의 본문을 나타내는 컴포넌트 |
| 레이아웃(layout) | 여러 경로가 공유하는 화면의 바깥 구조 |
| Server Component | 서버에서 실행하는 React 컴포넌트 |
| Client Component | 클라이언트 모듈 경계 안에 있는 React 컴포넌트 |
| hydration | 서버가 보낸 HTML에 브라우저의 React가 이벤트와 상태를 연결하는 과정 |
| Suspense | 비동기 콘텐츠를 기다리는 동안 대체 화면을 표시하는 React 경계 |
| 데이터 계약(data contract) | 컴포넌트나 요청 경계에서 주고받는 값의 모양과 뜻 |
| Server Action | UI에서 호출하는 변경 처리를 맡는 서버 함수 |
| Route Handler | `route.ts`에서 HTTP 요청과 응답을 다루는 처리기 |
| 캐시(cache) | 같은 조건의 요청에 재사용하는 계산·조회 결과 |
| 어댑터(adapter) | Next.js의 빌드 결과를 배포 환경의 실행 방식에 맞추는 연결부 |

상태 소유자는 `knowledge/domain/web-app-architecture.md` "개념", 공용 개념은 `knowledge/concepts.md`를 따른다.

## 관계

1. App Router의 경로 트리는 페이지가 속할 레이아웃을 정한다. 공유 레이아웃은 클라이언트 이동 때 상태를 유지하므로,
   문제 하나의 임시 상태를 공통 레이아웃에 두면 다른 문제로 옮긴 뒤에도 남을 수 있다. [S1]
2. `'use client'`는 가져오는 모듈의 경계를 정한다. 상태·이벤트·브라우저 API가 필요한 부분을 그 안에 두면 서버에서만
   가능한 처리를 바깥에 둘 수 있다. JSX의 부모·자식 관계만으로 실행 위치를 판별할 수는 없다. [S2]
3. Client Component도 첫 방문에는 HTML로 미리 보일 수 있지만, 조작하려면 JavaScript 전달과 hydration이 필요하다.
   따라서 HTML 응답의 성공만으로 문제 선택과 제출이 작동한다고 판단할 수 없다. [S2]
4. URL로 다시 읽은 props와 컴포넌트의 React 상태는 같은 것이 아니다. 문제 ID를 props에서 계산할 수 있는데도 상태로
   복사하면 경로가 바뀐 뒤 둘이 어긋날 수 있다. 같은 렌더 트리 위치·컴포넌트 타입·`key`를 유지하면 props가 바뀌어도
   React 상태는 남으므로, 문제별 컴포넌트로 옮기는 것만으로 답이 초기화되지는 않는다. 저장한 기록을 서버가 소유한다는
   것은 미구현 기능의 설계 제안이다. [S1, S3, S8] (잠정)
5. Server Component의 반환값도 Client Component의 props를 통해 브라우저로 전달될 수 있다. 데이터 계약을 화면에 필요한
   직렬화 가능한 값으로 좁히고 서버 모듈에 `server-only`를 붙이면 노출 범위와 잘못된 의존을 드러낼 수 있다. [S2, S4]
6. Server Action과 Route Handler는 서버에서 실행해도 외부 입력을 받는 경계다. 각 진입점에서 입력과 권한을 확인하고
   서버 전용 데이터 접근 계층에 처리를 모으면 화면마다 다른 접근 규칙이 생기는 것을 줄일 수 있다. [S4]
7. 서버의 변경 성공과 캐시를 읽는 화면의 갱신은 서로 다른 일이다. 변경 뒤 어떤 조회가 낡았는지에 맞춰 다시 읽거나
   `revalidatePath` 같은 무효화를 연결하지 않으면 저장한 뒤에도 예전 결과를 보여 줄 수 있다. [S4]
8. `use cache`는 빌드·함수 ID와 직렬화한 인수·캡처한 값을 키로 삼으므로 별도 `deploymentId`가 없으면 새 빌드는 이전
   결과를 재사용하지 않는다. 경로 사전 생성과 별개로 `cacheComponents`를 켜야 쓴다. 현재 앱은 설치 기본값과 설정을
   대조하면 이 기능이 꺼져 있으므로, 그 캐시 동작을 현재 경로의 동작으로 설명할 수 없다. [S5]
9. 빌드 때 알 수 있는 콘텐츠는 미리 렌더링할 수 있고 요청마다 필요한 값은 실행 중에 읽어야 한다. 이 차이는 컴포넌트가
   서버에 있는지와 별개다. Client Component도 미리 보일 수 있고 Server Component도 요청 때 실행할 수 있다. [S1, S2, S5]
10. 어댑터가 지원하는 기능과 런타임이 다르면 `next dev`에서의 성공이 배포 성공을 보장하지 않는다. 정적 파일 전달,
    Worker 바인딩과 브라우저 동작은 빌드 산출물을 실행하는 환경에서도 맞아야 한다. [S6, S7]
11. 공통 레이아웃에서 데이터를 기다리면 그 안의 화면도 함께 기다린다. Lighthouse는 검색 껍데기와 인증 뒤의 결과를
    나누고, 결과가 필요한 부분에 Suspense를 두었다. 이처럼 기다릴 데이터의 범위를 좁히면 먼저 보일 화면을 남길 수 있지만,
    보호 데이터의 인증·권한 검사를 생략할 수는 없다. [L1] (잠정)
12. 비동기 작업을 소유한 컴포넌트의 마운트 수명은 작업의 중단 시점에 영향을 준다. Lighthouse는 공통 경로의 작업과
    특정 렌더러의 작업을 나누고 떠난 뷰의 작업을 중단한다. 이를 적용하면 화면을 바꾼 뒤 옛 응답이 새 상태를 덮는 일을
    줄일 수 있다. 이 앱의 질문·학습 이동에 같은 효과가 있는지는 아직 확인하지 않았다. [L1] (잠정)

## 규칙

1. 경로의 공유 구조는 레이아웃에 두고, 문제별로 끝나야 하는 UI 상태는 그 문제의 컴포넌트가 소유하게 한다. (관계 1, 4)
2. 상호작용이 필요한 컴포넌트에서 클라이언트 경계를 시작하고, 서버 처리 모듈을 그 경계 안으로 가져오지 않는다. (관계 2, 5)
3. URL·props에서 계산할 문제 ID를 별도 React 상태로 복사하지 않는다. 작성 중인 답은 문제를 바꿀 때 유지할지 초기화할지
   정한다. 초기화는 문제 ID에 맞는 `key`·컴포넌트 식별성이나 명시한 상태 전이로 구현하고, 복원이 필요하면 문제별 값을
   보관하는 소유자를 따로 정한다. `key` 변경 자체가 이전 답을 복원해 주지는 않는다. (관계 1, 4)
4. Client Component에 넘길 props와 서버 처리의 응답은 필요한 필드로 좁힌다. 비밀값과 저장소 연결은 서버에 둔다. (관계 5)
5. 변경 진입점은 검증한 입력과 권한으로 처리하고, 저장 성공·실패·처리 중을 구분해 돌려준다. 버튼 비활성화를 중복 저장
   방지의 근거로 삼지 않는다. (관계 6)
6. 변경 뒤 다시 읽어야 할 조회를 정하고, 실제로 캐시한 경로·데이터에 맞는 무효화를 연결한다. (관계 7)
7. 공통 콘텐츠와 개인별 요청 데이터를 구분해 렌더링 방식을 고른다. `cacheComponents`를 켜지 않은 앱에 그 기능을
   전제한 예제를 그대로 적용하지 않는다. (관계 8, 9)
8. Next.js·React·어댑터의 설치 버전과 설정에 맞는 지원 범위를 확인한다. 바인딩을 쓰는 기능은 Workers 미리보기와
   배포 환경에서 검증하고, 설정 변경이 빌드에 반영된 산출물을 사용한다. (관계 10)
9. 브라우저 검증은 본문 표시와 함께 JavaScript·CSS 전달, 선택·입력·제출의 결과를 확인한다. 새로고침 후 복원은
   해당 기능을 구현한 뒤 확인한다. (관계 3, 4, 10)
10. 먼저 보일 화면과 반드시 기다릴 데이터를 나누고 그 경계에 Suspense를 둔다. 인증 뒤에만 보일 값은 보호된 서버
    경계에서 읽는다. (관계 11) (잠정)
11. 비동기 작업은 문제·경로·렌더러 가운데 실제 수명에 맞는 컴포넌트가 소유하게 한다. (관계 12) (잠정)

## 배운 것

- 2026-10-26 전환 구현 검증에서는 빌드 뒤 바꾼 `run_worker_first` 설정이 산출물에 반영되지 않아 HTML은 열렸지만
  JavaScript·CSS가 404가 되고 조작이 작동하지 않았다. 설정을 반영해 다시 빌드한 뒤 해결했다. 빌드와 정적 파일 경로가
  hydration의 전제라는 관계 3, 10을 이 앱에서 관찰했다. 강PD의 학습 수행 기록이 아닌 구현 검증이며 한 맥락의 결과다. (잠정)

## 한계와 출처

- 공식 문서에서 확인한 관계와 이 앱의 적용 가설을 구분했다. 자료와 검토 범위는 [조사 노트](../../docs/research/nextjs-development.md)에 있다.
- Lighthouse `df85ac9a6f09c569d0e01b83ebdca4eebc996ea5`의 구현 규칙과 코드·테스트를 읽었다. 관계 11, 12는 그 구조를
  이 앱의 판단에 옮긴 잠정 관계다. 원본 테스트를 실행하지 않았고 Lighthouse의 운영 성공으로 확정하지 않았다.
- 2026-10-26 설치 확인: Next.js 16.4.3, React·React DOM 19.3.1, OpenNext Cloudflare 1.20.13. 설치 패키지의
  `defaultConfig.cacheComponents`는 `false`이고 `next.config.ts`는 이를 바꾸지 않는다. 최신 문서의 기본값을 일반화하지 않는다.
- 현재 앱은 공통 콘텐츠를 미리 만들고 해설 요청을 Route Handler로 처리한다. 개인 기록 저장과 Server Action은 아직
  구현하지 않았다. 관련 규칙은 다음 개발을 위한 판단 기준이며 이 앱의 성공 사례로 확인하지 않았다.
- 같은 Worker의 Durable Object를 `next dev`가 실행하지 못한 조건은 `README.md`에 있다. 실제 운영 동작 전체와
  개인 학습의 편리함은 이 모델을 썼다는 이유만으로 확인되지 않는다.
