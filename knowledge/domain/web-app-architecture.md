# 도메인 모델: 웹앱 아키텍처

웹앱의 책임을 어디에 두고 요청·상태·의존성을 어떻게 연결할지 판단할 때 쓴다. 브라우저, 서버, 저장소와 외부 서비스가
함께 한 동작을 처리하는 구조를 설명한다. 제작의 목적과 품질은 [웹앱 제작 모델](web-app-production.md), Next.js의 구체적인
실행 방식은 [Next.js 개발 모델](nextjs-development.md), 일을 진행하는 방법은 `knowledge/production.md`가 맡는다.

## 개념

| 개념 | 뜻 |
| --- | --- |
| 책임(responsibility) | 한 구성 요소가 맡는 판단과 동작의 범위 |
| 의존성(dependency) | 한 구성 요소가 동작하려고 다른 요소에 기대는 관계 |
| 실행 경계(runtime boundary) | 코드를 실행하는 위치나 환경이 달라지는 지점 |
| API 계약(API contract) | 요청과 응답의 형태, 허용한 동작과 실패의 뜻에 관한 약속 |
| 신뢰 경계(trust boundary) | 데이터나 행위자의 신뢰 수준이 달라지는 지점 |
| 인증(authentication) | 요청자가 누구인지 확인하는 일 |
| 인가(authorization) | 요청자가 특정 자원에 특정 동작을 할 수 있는지 판단하는 일 |
| 상태 소유자(state owner) | 어떤 상태의 변경을 최종 결정하는 주체 |
| 내구성(durability) | 상태가 정해 둔 중단이나 재시작 뒤에도 남는 성질 |
| 불변 조건(invariant) | 허용한 상태 변화 전후에 항상 참이어야 하는 조건 |
| 원자성(atomicity) | 묶은 변경이 모두 적용되거나 모두 적용되지 않는 성질 |
| 격리성(isolation) | 동시에 실행하는 변경이 서로의 중간 상태에 간섭하지 않는 성질 |
| 멱등성(idempotency) | 같은 동작을 반복해도 한 번 적용한 것과 결과가 같은 성질 |
| 캐시 키(cache key) | 재사용할 데이터를 구별하는 값 |
| 최신성(freshness) | 읽은 데이터가 현재 상태를 반영하는 정도 |
| 배포 단위(deployment unit) | 함께 내보내거나 호환성을 유지해야 하는 실행 요소의 묶음 |
| 구조적 방어(structural defense) | 지킬 경계나 불변 조건의 위반을 막거나 드러내는 코드·검사 장치 |
| 실행 식별성(execution identity) | 같은 자료·화면에서도 각각의 처리 실행을 구별하는 기준 |

브라우저·서버·저장소·외부 서비스는 실행 위치를 가리키는 일반 용어로 쓴다. 공용어는 `knowledge/concepts.md`를 따른다.

## 관계

1. 화면이 외부 API나 저장 형식을 직접 알면 그 형식의 변경이 화면까지 퍼진다. 화면과 처리 책임 사이에 API 계약을 두면
   변경이 전파되는 범위를 그 계약으로 제한할 수 있다.
2. 브라우저의 실행과 요청은 사용자가 바꿀 수 있으므로 화면의 입력 제한만으로 서버가 지킬 불변 조건을 보장할 수 없다.
3. 인증은 요청자의 신원을 밝혀도 자원별 권한까지 정하지 않으므로, 인증된 요청도 인가가 없으면 다른 사람의 상태에 닿을 수 있다.
4. 브라우저가 보낸 데이터와 외부 서비스의 응답은 계약을 어길 수 있으므로, 실행 위치를 옮기는 것만으로 입력과 출력의
   형태나 의미가 보장되지는 않는다.
5. 상태를 바꿀 소유자가 여러 곳에 있고 변경을 조정하지 않으면 각 사본이 서로 다른 값을 확정할 수 있다.
6. 상태를 보관한 곳의 수명보다 오래 남아야 하는 상태는 그곳이 사라질 때 잃는다. 다른 기기나 실행 인스턴스가 같은 상태를
   읽어야 한다면 그들이 접근할 수 있는 저장 경로도 필요하다. 남아 있는 값도 사용자·자료 버전이 다르면 현재 상태로 합성할 수 없을 수 있다.
7. 여러 요청이 같은 값을 읽고 따로 바꾸면 각각 올바른 검사도 함께 지킬 불변 조건을 깨뜨릴 수 있다. 검사와 변경의
   원자성·격리성이 보장되면 그 범위 안에서 다른 요청이 중간 상태에 끼어들어 조건을 깨뜨리는 일을 막을 수 있다.
8. 저장소의 트랜잭션은 그 경계 밖의 외부 호출까지 함께 되돌리지 못한다. LLM 호출과 로컬 기록 사이에서 실패하면
   호출의 성공, 비용 발생과 기록의 성공이 서로 어긋날 수 있다.
9. 응답을 못 받은 요청도 서버에서는 끝났을 수 있으므로 같은 요청을 다시 보내면 변경이나 외부 비용이 중복될 수 있다. 시간 초과는 확정 실패뿐 아니라 결과 불명일 수 있다.
10. 캐시는 같은 캐시 키에 같은 결과를 재사용하므로 결과를 가르는 사용자·권한·입력이 키나 재사용 조건에서 빠지면 다른 결과를
    돌려줄 수 있다. 원본이 바뀌어도 기존 사본을 재사용하면 최신성이 낮아진다.
11. 실행 코드는 설정·바인딩·데이터 구조를 전제로 동작하므로 코드만 바꿔도 이 전제가 어긋나면 배포 뒤 실패할 수 있다.
12. 외부 서비스와 저장소는 각각 실패할 수 있으므로 한 요청의 성공 여부는 구성 요소 하나의 정상 상태만으로 알 수 없다.
13. 여러 계층이 같은 계약을 따로 정의하면 한쪽만 바뀔 수 있다. 하나의 순수한 계약에서 타입과 검사를 파생하면 뜻의 중복을 줄일 수 있다.
14. 같은 화면 행동도 저장 기간·공유 범위·권한·복구 기대가 달라지면 상태 소유자와 실행 경계가 달라질 수 있다.
15. 정적 의존성 검사는 금지한 연결의 재도입을 드러낼 수 있지만, 허용한 연결 안의 실행 순서나 사용자 결과까지 증명하지는 못한다.
16. 중단 요청을 받은 전송도 응답하거나 서버 처리를 끝낼 수 있다. 같은 자료를 다시 연 새 실행과 이전 실행을 구분하지 않으면 늦은 결과가 새 상태를 덮을 수 있다. (잠정)

## 규칙

1. 화면, 서버 처리와 외부 연동의 책임을 나누고 요청·응답·실패의 뜻을 API 계약에 명시한다. 화면에 외부 서비스의
   비밀 값이나 저장소의 내부 구조를 넘기지 않는다. (관계 1, 2)
2. 입력·출력의 형태와 크기를 신뢰 경계에서 검사하고, 내용의 타당성을 형식 검사 통과와 구별한다. LLM이 구조에 맞게
   답했다는 사실만으로 그 해설이 맞다고 확정하지 않는다. (관계 4)
3. 개인 상태와 비용이 드는 동작은 요청마다 허용 정책을 적용한다. 개인용이라는 목적, 같은 출처의 API나 IP별 횟수 제한을
   개인 인증과 인가의 근거로 삼지 않는다. (관계 2, 3)
4. 상태마다 최종 변경 주체, 필요한 내구성과 함께 읽을 범위를 정하고 그 조건을 만족하는 저장소를 고른다. 복원할 때 사용자·자료 버전에 따라 값의 의미가 달라지면 그 범위도 대조한다. (관계 5, 6)
5. 함께 지켜야 할 불변 조건을 먼저 밝히고 검사와 변경의 원자성·격리성 범위를 맞춘다. SQL의 조건부 갱신·트랜잭션과 요청을
   한곳에서 조정하는 객체 가운데 필요한 보장을 주는 쪽을 고른다. (관계 7)
6. 외부 호출과 저장이 갈라지는 동작은 중간 실패가 남길 상태를 정한다. 재요청을 허용할 때 중복 판별과 멱등성의 범위를
   밝히고 결과 불명에서는 같은 동작의 저장값 조회·재시도 정책을 정한다. 로컬 중복 방지만으로 외부 호출 비용까지 한 번만 발생한다고 보장하지 않는다. (관계 8, 9)
7. 캐시를 쓰는 데이터마다 누구에게 재사용해도 되는지, 얼마나 오래된 값을 허용할지와 무엇이 사본을 무효로 하는지 정한다.
   개인 응답은 공개 응답과 공유하지 않고, HTTP 설정뿐 아니라 앱이 직접 관리하는 캐시도 확인한다. (관계 10)
8. 배포 단위를 코드·설정·비밀 값·바인딩·데이터 구조의 조합으로 본다. 이전 코드와 새 구조의 호환성을 별도로 판단하고,
   코드 복귀를 데이터 복구와 같은 것으로 취급하지 않는다. (관계 11)
9. 요청마다 실패한 책임을 구별할 수 있게 하되 사용자에게는 다음 행동이 가능한 실패를 돌려준다. 일부 단계만 끝났다면
   전체가 완료됐다고 응답하지 않는다. (관계 8, 12)
10. 여러 실행 위치가 공유하는 뜻은 효과를 일으키지 않는 계약 모듈이 소유하게 한다. 저장 형식과 화면 형식처럼 뜻이 다른
    값은 억지로 합치지 않고 변환 경계에서 보존하거나 버리는 내용을 밝힌다. 기존 값 읽기의 호환 정책을 새 변경 입력의 허용 정책으로 그대로 쓰지 않는다. (관계 1, 4, 13)
11. 승인된 기대가 달라지면 현재 소유자가 감당할 수 있는지 판단하고, 바꿀 소유자와 살펴볼 하위 의존성, 호환 대상과
    은퇴 대상을 구별한다. 구조를 유지하거나 바꾸는 까닭과 거부한 대안을 남긴다. (관계 5, 11, 14)
12. 반복해 지킬 경계에는 위반 사례를 잡는 구조적 방어를 두되, 그 검사로 확인한 범위를 실행 결과와 구별한다. 폴더와
    검사 수를 늘리는 것으로 구조가 낫다고 판단하지 않는다. (관계 1, 15)
13. 비동기 작업의 실행 식별성과 결과 채택 조건을 정하고, 취소 요청과 별도로 응답 시점에도 대조한다. 응답은 자신이 소유한 필드만 갱신하며 더 최신 상태를 통째로 덮지 않는다. (관계 5, 16) (잠정)

## 한계와 출처

- [공식 자료 조사와 적용 범위](../../docs/research/web-app-architecture.md)를 근거로 2026-10-26 짰다. 관계를 이 프로젝트의
  구조 판단에 묶은 것은 설계 추론이며, 이 모델을 배경에 둔 작업이 나아졌는지는 아직 확인하지 않았다. (잠정)
- 현재 사례는 정적 공개 페이지, Worker의 해설 API와 사용량 Durable Object다. 개인 기록 DB와 개인 인증·인가는 아직
  구현하지 않았다. D1은 후보이며, 외부 호출과 저장을 함께 처리하는 신뢰성이나 개인 기록 캐시는 검증하지 않았다.
- D1도 SQL 트랜잭션을 제공한다. Durable Object 선택을 D1의 트랜잭션 부재로 설명하지 않는다. 특정 Cloudflare 제품을
  쓰는 것은 이 모델의 보편 규칙이 아니며, 구체적인 선택과 플랫폼 한도는 조사 문서와 실행 설정에서 확인한다.
- Lighthouse의 상태 소유 지도·중립 계약·변경 영향 분류·의존성 방어를 자료로 삼았다. 조직의 승인 체계와 전체 검사 도입은
  승인하지 않았고, 이 개인 앱에서 그 기법의 효과도 아직 확인하지 않았다. 기준 커밋과 확인한 코드는 조사 문서에 있다.
- 결과 불명·사용자와 자료 버전에 맞는 복원·취소와 응답 채택의 분리는 `docs/research/lighthouse-contract-engineering.md`의 두 코드 사례에서 가져왔다. 원본을 재실행하지 않았고 개인 학습 API에 아직 적용하지 않았다.
