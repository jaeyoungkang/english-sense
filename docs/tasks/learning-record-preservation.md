# 풀이 과정의 기록과 보존

## 과업과 승인 근거

- 과업: 강PD가 처음 낸 답부터 힌트·수정·질답을 거쳐 생각이 달라진 과정을 당시 자료와 실제 발생 순서로 다시 읽고, 멈춘 초안에서 이어 쓴다.
- 승인 근거: [#5](https://github.com/jaeyoungkang/english-sense/issues/5)의 2026-10-26 지시인 “풀이과정도 다 기록으로 남겨둬야한다”와 [서비스 요구](../learning-service.md)의 수행 차이·맥락 복원 약속이다. 이번 세션에서는 이슈 검토 뒤 현황 갱신, 보존 범위 구체화, 디자인 결정 정리 순서로 진행하도록 승인했다.
- 범위 결정: 2026-10-28 강PD가 제시한 네 범위 선택에 “모두 권고대로하라”고 답했다. #5는 홈 have 1개·이야기 15편·카드 13유닛의 작업 공간 29개(v3+v4)를 먼저 다룬다. 정적 연습·펜 노트의 보존 확대는 후속으로 둔다.
- 이번 범위: 현재 기록과 유실 경계를 조사하고, 승인된 29개 작업 공간의 보존 요구를 수용 조건으로 구체화한다. 이번 기획에서는 보관·접근·복구·정본 이관의 구체적인 정책안과 구현 경계를 제안한다. 앱 구현·운영 설정·실제 학습 기록 변경은 하지 않는다. 정책안은 화면 범위 승인에 포함되지 않았으며 아래에서 채택 여부를 판단한다.
- 현재 구현: have 작업 공간은 v3, 이야기·카드 수업은 수업별 v4, 펜 노트는 별도 v1을 브라우저에 보관한다. 정적 연습은 화면을 떠날 때 복원할 기록이 없다. 개인 인증·서버 기록 DB·다른 기기 복원·기존 정본 기록 연결은 없다.
- 기대: 현재 보관하는 사실과 빠진 사실을 구분하고 저장 경계를 정하면, 화면 복원만 성공한 상태를 과정 보존 완료로 잘못 판단하지 않을 수 있다.
- 기대의 근거: [웹앱 제작 모델](../../knowledge/domain/web-app-production.md) 규칙 2·6·8, [UX 모델](../../knowledge/domain/web-app-ux-design.md) 규칙 9·12·14·19, [구조 모델](../../knowledge/domain/web-app-architecture.md) 관계 6·8·9·14와 규칙 4·6·13이다. 기대와 실행을 구분하는 방법은 [제작 모델](../../knowledge/production.md)의 규칙을 따른다.
- 가를 관찰: 실제 화면 입력으로 생성한 기록을 저장 경계 밖에서 다시 읽었을 때 최초 답·수정·요청별 결과·초안의 내용과 연결이 맞는지 본다. 화면에 저장 표시가 있다는 사실만으로 보존을 판정하지 않는다.

대상 화면의 범위는 승인됐으며 저장 정책을 정하기 위한 계약 초안이다. 학습 자료와 기존 학습 기록의 정본은 study-and-learn 프로젝트에 둔다. 실제 답·질문·응답 원문을 이 문서나 새 파일에 옮겨 중복 관리하지 않는다. 웹 기록을 정본과 연결하는 방식은 아직 정하지 않았다.

## 시작과 끝

- 시작 상황: 작업 공간 29개와 문장 해설기(`/ask/`) 중 한 곳에서 기존 임시 기록을 열거나 빈 브라우저로 문제를 읽고 답·이유·질문·해설 문장을 쓰기 시작한다.
- 사용자 행동과 서비스 반응: 본문에서 답을 제출하고 다른 문제를 풀다가 수정·질답을 이어 가거나 `/ask/`에서 문장 해설과 이어 묻기를 진행하면, 서비스는 최초 답을 덮지 않고 실제 요청·응답·중단과 초안을 구분해 남긴다. 사용자는 당시 자료와 함께 문제별 전문과 실제 순서의 요약을 다시 읽는다.
- 기대 결과: 비로그인 상태에서는 브라우저 임시 보관으로 동작하고, Cloudflare Access로 로그인한 상태에서는 학습자 전용 SQLite Durable Object에 과정 원문과 최신 초안을 보관해 페이지를 닫거나 다른 기기에서 열어도 제출·수정·질답과 작성 중인 상태를 구별하고 이어 쓴다.
- 실패 뒤 다음 행동: 저장 실패는 화면에 남은 값과 보관된 값을 구분해 알리고 저장 재시도를 제공한다. 요청 결과를 모르면 성공·확정 실패로 단정하지 않고, 다시 보내는 행동과 저장된 결과를 확인하는 행동을 구분한다. 복원 자체가 요청을 자동 재전송하지 않는다.
- 이번 범위 밖: 정적 연습·펜 노트의 보존 확대, 숙달·완료·진행률·복습 간격의 도입, 정본 학습 내용 수정, 기존 답·이유가 없는 형식의 임의 확대, 정적 퀴즈 정답의 서버 이관, AI 설명 정확성이나 학습 효과의 자동 판정이다.

### 정본 연결에서 확인한 차이

2026-10-28 study-and-learn의 `learn/README.md`·영어 학습 기록 구조와 이 프로젝트의 가져오기 경로를 읽었다. 개인 답·질문·AI 응답 원문을 이 문서에 옮기지 않았다.

- study-and-learn `learn/english-as-germanic/attempts.jsonl`은 `date`, `problem_id`, `first_answer`, `hints`, `revised_answer`, `chose`, `reason`, `qa`, `note`를 쓴다. 유닛 문서는 수행·피드백을 설명하고 풀이 원문은 이 파일을 가리킨다. 기존 기록은 고쳐 쓰지 않는 원칙이다.
- 현재 형식은 자료 판·실행/요청/스레드 ID·복수 수정·초안·요청별 실패를 온전히 담지 못한다. 웹 과정을 이 형식으로 압축하거나 AI 요약으로 바꾸면 보존 요구를 잃는다. **정본에 웹 과정 원문을 담는 형식과 위치를 승인하는 일이 필요하다.** 제안 위치는 study-and-learn의 `learn/english-as-germanic/web-process/<bundleId>.json`이다. 아직 없는 제안 경로이며 기존 attempts·유닛 기록을 덮지 않는다.
- 전송 묶음은 `schemaVersion`, `bundleId`, `ownerId`, 저장 세대와 수신 순번 범위, 과정 사건, 자료 판 참조, 옛 기록 원문, 이관 시점의 초안 스냅샷과 전송 내용 해시를 가진다. 실제 값은 검증 입력 또는 실제 수집 원문에서만 만든다. 정본 파일은 새로 받은 원문과 이미 보관한 원문을 가리키는 참조, 전송 해시와 정본 파일 해시를 구분해 담는다. 전송 해시를 정본 파일 자체의 해시라고 잘못 기록하지 않는다.
- 수신 측은 묶음 ID뿐 아니라 **소유자·실행 ID·사건 ID와 사건 내용 해시**를 대조한다. 같은 사건이 다른 묶음으로 다시 와도 원문은 한 번만 보관하고 기존 정본 위치를 참조한다. 같은 사건 ID에 다른 내용이 오면 묶음 전체를 거절한다. 초안 스냅샷·옛 기록 원문·자료 본문도 고유 식별과 내용 해시로 중복을 가른다. 이미 이관한 파일을 고쳐 쓰지 않는다.
- 웹 have의 `titanic-have-1`~`7`은 정본 문제 ID와 다르다. 내용 근거가 있는 명시적 대응표를 만들고, 대응을 확정하지 못하면 원래 웹 ID를 유지한다. 이야기·카드는 원본 문제/카드 ID를 유지한다. 같은 문제를 다시 푼 것과 같은 전송의 중복은 실행·사건 ID로 구분한다.
- `scripts/import-study-content.ts`는 자료만 단방향으로 가져오며 학습 기록 API·동기화·정본 이관 도구는 없다. 제안 흐름은 **서버 수집 → 인증된 원문 내보내기 → 정본에서 검증·중복 판별·보관 → 수신 확인**이다. 수신 확인은 소유자·묶음 ID·마지막 수신 순번·원문 해시를 연결하며, 단순 내려받기 성공을 정본 보관으로 세지 않는다.
- 이관 전 서버 원문은 “정본 반영 대기”, 이관 뒤 서버 조회 자료는 정본의 식별·수신 확인을 가진 사본으로 표시한다. 원문 보관 형식·장소·도구는 study-and-learn 쪽 설계 승인 뒤 구현한다. 이번 기획에서 다른 저장소 파일이나 실제 기록은 바꾸지 않는다.

### 저장·요청 계약의 구현안

다음은 정책안이 채택됐을 때 사용할 기술 경계다. 특정 저장소 도입 자체로 개인 기록의 보존을 완료했다고 보지 않는다.

| 단위 | 필요한 식별과 불변 조건 |
| --- | --- |
| 저장 명령 | `commandId`, 수업·실행·문항·자료 판, `expectedRevision`을 받는다. 소유자는 서버가 결정한다. 같은 명령 ID·같은 본문은 기존 결과를 돌려주고, 같은 ID·다른 본문은 충돌로 거절한다 |
| 과정 사건 | 사건 ID·실행 ID·종류·연결 대상과 원문을 보존한다. 새 사건과 현재 상태/revision을 같은 저장 트랜잭션으로 반영한다. 사건 배열이 없는 과거 기록은 원문 묶음으로 남긴다 |
| 자료 판 | 서버가 확보한 당시 공개 자료와 판·해시를 연결한다. 옛 브라우저 스냅샷은 출처를 구분하고, 없는 과거 이야기 본문은 현재 본문으로 대체하지 않는다. 복원 API도 첫 답 전 정답·카드 표현을 노출하지 않는다 |
| 초안 | 대상·기기·revision별 최신 값과 마지막 동기화 상태를 보존한다. 낡은 전체 상태 JSON으로 새 사건·응답을 덮지 않는다. 저장 실패 시 화면·로컬 대기열·서버 확인 값을 구분한다 |
| 외부 실행 | 논리 요청과 실행 시도를 분리한다. 실행은 `queued → dispatching → succeeded / failed / unknown`으로 관리하고 결과 원문을 외부 호출의 재실행 없이 조회한다. 취소·재시도는 이전 시도를 덮지 않는 사건이다 |
| 정본 이관 | 묶음 ID·스키마 판·자료 판·실행/사건 ID·원문 해시를 가진 내보내기와 수신 확인을 쓴다. 같은 묶음 재이관과 서로 다른 묶음의 같은 사건을 모두 중복 판별한다. 같은 ID에 다른 내용이면 묶음 전체를 거절한다. 복구로 수신 순번이 되돌아갈 때는 저장 세대와 사건 ID를 함께 대조한다 |

이벤트 저장 성공과 외부 AI 성공은 한 트랜잭션이 아니다. 실행 시작 뒤 결과 저장 전에 중단됐으면 `unknown`으로 남긴다. DO alarm은 중복 실행될 수 있으므로 `dispatching`인 외부 호출을 무조건 재실행하지 않게 한다. 복구도 새 실행을 자동 생성하지 않는다. 원래 서버가 만들지 못한 결과는 복구됐다고 표시하지 않는다.

### 플랫폼 근거와 선택 한계

2026-10-28 공식 문서를 확인했다. 아래는 플랫폼 사실이며 위 보관·삭제·정본 정책의 승인이나 이 앱의 실행 결과는 아니다.

- [SQLite Durable Object 저장 API](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/)는 강한 일관성·트랜잭션 저장과 최근 30일 시점 복구를 제공한다. 시점 복구는 로컬 개발에서 지원하지 않는다. 제안의 선택 이유는 학습자별 사건·중복 판별·현재 상태의 조정 책임을 한 저장 경계에 두기 위해서다. D1도 가능한 대안이며 트랜잭션이 없어서 제외하는 것이 아니다.
- [Access JWT 검증](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/validating-json/)은 Worker에서도 토큰 서명·발급자·대상을 확인하는 경로를 제공한다. [Workers Access의 `ctx.access` 제한](https://developers.cloudflare.com/workers/configuration/cloudflare-access/#ctxaccess-limitations)에 따르면 Static Assets 내부 라우터는 그 컨텍스트를 사용자 Worker에 전달하지 않는다. 현재 앱은 Assets를 사용하는 OpenNext Worker이므로 네이티브 신원 컨텍스트를 가정하지 않고 JWT 검증을 기본 후보로 둔다.
- [DO alarm](https://developers.cloudflare.com/durable-objects/api/alarms/)은 최소 한 번 실행이며 실패 시 재시도한다. 실행 재호출 제어와 결과 불명 처리는 앱이 맡아야 한다. 현재 `DailyQuota`는 48시간 뒤 `deleteAll()`을 실행하므로 학습 기록과 공유하지 않는다.
- 새 개인 경로만 보호해 공개 학습·기존 API 주소를 유지한다. `workers.dev`·preview·기존 API 도메인으로 들어온 개인 요청도 인증·허용 호스트 검사를 피할 수 없어야 한다. 실제 Access 앱 생성, 허용 사용자 설정, Workers 바인딩·마이그레이션·비밀 설정은 아직 하지 않았다.

### 승인 뒤 구현할 순서

1. **신원과 최소 보관 경계:** 격리된 사용자·새 저장 객체로 인증→명령 쓰기→같은 명령 재전송→독립 조회→다른 브라우저 재개를 확인한다. 미인증·타 소유자·대체 호스트·저장 실패·revision 충돌도 함께 확인한다.
2. **기존 기록과 당시 자료:** v1/v2/v3 원문·v4를 손실 없는 가져오기 묶음으로 남기고, v3/v4 화면이 새 실행·보관함·초안에 연결되게 한다. 읽기·판정·답 보기·요청 실패의 실제 생성 순서를 확인한다. 기존 노트의 저장 경계는 유지한다.
3. **질답과 중간 실패:** 요청별 이력을 먼저 남기고 서버 결과 조회를 연결한다. 외부 호출 뒤 중단·시간 초과·결과 저장 실패·늦은 응답·새 대화를 유발해 기존 과정을 덮거나 자동 유료 재실행하지 않는지 확인한다.
4. **정본 이관과 복구:** 승인된 정본 원문 형식과 가져오기 도구로 묶음을 보관한다. 같은 묶음 재이관, 다른 묶음의 같은 사건, 같은 사건 ID·다른 내용, 이관 중단 뒤 재개, 손상·누락·옛 자료 판·복구 뒤 대조를 확인한다. 초안의 최신 동기화와 이관 시점 스냅샷도 구분해 확인한다. 실수 기록과 검증 입력을 실제 학습 기록에 섞지 않는다.
5. **전체 회귀와 운영 확인:** 29개 수업의 기존 입력·공개 시점·판정·AI·노트·레이아웃 경계를 검사한다. 운영에서는 승인된 자원·배포 범위 안에서 실제 로그인·쓰기·조회·다른 기기 복원까지 확인한다.

정책 채택에 대한 실제 응답은 아직 없다. 이미 확정한 화면 범위는 다시 묻지 않는다. 새로 판단할 것은 위 정책안과 study-and-learn의 과정 원문 형식 추가다. 사용 뒤 지난 생각과 중단 지점을 쉽게 찾아 이어 쓸 수 있는지는 별도로 강PD가 판단한다.

## 사용자 경험과 구조 영향

첫 답·수정의 전문은 문제 안에 두고 실제 순서 요약과 질문은 옆 대화에 연결한다. 현재 화면 배치·본문 읽기 위치를 바꾸는 디자인 작업으로 확대하지 않는다. 재개할 때 제출한 답·작성 중 초안·받지 못한 응답·저장 범위를 구분한다. 저장·응답 알림은 키보드 초점을 빼앗지 않고 좁은 화면에서도 읽고 다시 시도할 수 있어야 한다. 기존 펜 노트의 가린 본문을 공개하지 않는 경계도 유지한다. 이는 구현 시 지킬 기존 UX 조건이며 새 화면의 사용성 검증 결과는 아니다.

- 구조 기대의 변화: 브라우저에 남은 현재 상태에서 과정별 사실과 정한 수명을 가진 보관으로 넓어진다. 저장 범위·실행 식별·자료 판·요청 결과의 소유자를 명시해야 한다.
- 영향: 향후 구현은 **reshape 예상**이다. 이번 변경은 계약 문서 작성뿐이며 현재 구조를 바꾸지 않는다. 저장·인증·정본 연결 정책을 고른 뒤 실제 영향과 범위를 확정한다.
- 현재 소유자: v3/v4의 reducer가 학습 상태를, `learning-thread.ts`가 대화 수명주기를, `workspace-session.tsx`가 브라우저 저장·AI 요청을, `lesson-common.tsx`가 판정 요청을 맡는다. 펜 노트와 문서/레이아웃 상태는 별도다.
- 경계 권고: 제출 사실·요청 시도·응답 결과·초안을 구분하고, 재시도가 과거 사실을 덮지 않게 한다. 외부 AI 호출 성공과 기록 저장 성공의 중간 실패·결과 불명을 별도로 다룬다. 저장 방식·API·스키마의 기술안은 위에 제시했고 정책 채택 뒤 확정한다.
- 채택하지 않을 대안: 전체 문서 표시·현재 힌트 글·현재 턴 상태에서 과거 수행이나 실패 이력을 만들어 채우는 방법은 승인된 사실 보존에 어긋난다. localStorage만 성공시키고 지속 보존을 완료로 표시하는 방법도 #5의 완료 조건에 어긋난다.
- 구현 때 함께 고칠 문서: [아키텍처](../architecture.md)의 기록·요청·보관 책임과 [서비스 요구](../learning-service.md)의 현재 구현·남은 경계를 실제 변경에 맞춘다. 승인된 약속의 뜻을 새로 정해야 하면 강PD의 판단을 받는다.

## 변경 범위와 구현 인계

다음 구현에 넘길 자료는 이 계약, [shared-skills/web-app-implementation/SKILL.md](../../shared-skills/web-app-implementation/SKILL.md), 제작·UX·구조 모델과 `knowledge/production.md`다. 먼저 미결 정책을 확정해 계약의 조건부 행을 구체화한다. 그 뒤 선택한 저장 경계를 통과하는 최소 실행으로 쓰기·조회·복원을 확인하고 v3/v4·대화·판정·자료 판·초안의 필요한 경로를 바꾼다.

호환 대상은 v1/v2/v3 원문, 기존 v4·노트, 당시 자료 판과 현행 수업 주소다. 은퇴할 기록 형식은 정하지 않았다. 정적 퀴즈 정답 공개 경계·학습 효과·디자인 통일은 영향만 살피며 이 계약의 보존 조건으로 함께 해결하지 않는다.

요구가 충돌하거나 선택한 저장 방식이 수명·권한·정본 정책을 만족하지 못하면 우회하지 않고 충돌과 선택지를 보고한다. 같은 확인을 고치고 다시 재는 일이 3회를 넘으면 멈추고 원인을 보고한다.
